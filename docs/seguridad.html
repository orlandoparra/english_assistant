Seguridad y Tokens

Cómo se protegen las contraseñas (hash Argon2) y cómo funciona la sesión (token JWT)

Documento de referencia · refleja lo implementado en el backend (FastAPI)

🎯 Objetivos del sistema de seguridad

🛡️ Proteger los datos

La contraseña nunca se guarda tal cual; solo su hash irreversible.

🔐 Sesión segura

Tras el login, un token firmado identifica al usuario en cada petición.

⚡ Acceso sin estado

El token lleva la info necesaria, así el servidor no guarda sesiones.

🌐 Base moderna

Algoritmos recomendados hoy (Argon2, JWT HS256).

¿Por qué se hace así?

  • Privacidad: nadie puede ver las contraseñas, ni siquiera quien administra la base de datos.
  • Estándares: se siguen prácticas recomendadas (OWASP para el hash, RFC 7519 para el token).
  • Confianza: aunque la base de datos se filtrara, las contraseñas no quedarían expuestas.

🔒 Hash de contraseñas (Argon2)

La contraseña real nunca se guarda. Solo se almacena su hash, y de un hash no se puede volver a la contraseña.

Flujo al registrarse

1
El usuario escribe su contraseñaEjemplo: MiClave123
↓
2
El sistema aplica Argon2Proceso de hashing irreversible, con salt único por usuario
↓
3
Se guarda solo el hash$argon2id$v=19$m=65536,t=3,p=4$... · nadie puede ver la contraseña original

Características

  • ✅ Argon2, el algoritmo de hashing de contraseñas recomendado actualmente (ganador del Password Hashing Competition).
  • ✅ Irreversible: no existe forma de "descifrar" el hash para obtener la contraseña.
  • ✅ Salt único por usuario: dos personas con la misma contraseña tienen hashes distintos.
  • ✅ Lento a propósito: dificulta los ataques de fuerza bruta.
¿Cómo se verifica al entrar? No se "descifra" el hash. Se vuelve a hashear la contraseña que escribe el usuario y se compara con el hash guardado. Si coinciden, la contraseña es correcta. Esto lo hace verify_password() en app/core/security.py.

🔑 ¿Qué es un token JWT?

JWT (JSON Web Token) es un estándar abierto (RFC 7519) para transmitir información de forma compacta y verificable entre el frontend y el backend. Al iniciar sesión, el backend crea un token firmado; el frontend lo guarda y lo envía en cada petición protegida para demostrar quién es el usuario.

Estructura

Un JWT tiene tres partes separadas por puntos: header.payload.signature.

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbmFAZ21haWwuY29tIiwiZXhwIjoxNzMwMH0.Kq3b...firma
1HEADER (encabezado)
Indica el tipo y el algoritmo de firma.
{ "alg": "HS256", "typ": "JWT" }
2PAYLOAD (datos)
En nuestro caso lleva el correo del usuario (sub) y la caducidad (exp).
{ "sub": "ana@gmail.com", "exp": 1730001234 }
3SIGNATURE (firma)
Garantiza que el token no fue modificado. Se calcula con la clave secreta del servidor.
HMACSHA256(header + payload, SECRET_KEY)
Importante: el payload va codificado en Base64, no cifrado. Cualquiera puede leerlo, así que nunca se ponen datos sensibles (ni la contraseña). Lo que impide falsificar un token es la firma: sin la clave secreta del servidor no se puede generar una firma válida.

⚙️ Qué hay implementado y qué no

✅ Implementado

  • Hash Argon2 de la contraseña (passlib), en app/core/security.py.
  • Token JWT HS256 con caducidad de 30 minutos, firmado con la clave secreta del .env.
  • Verificación del token en cada ruta protegida (GET /auth/me).
  • Correo normalizado a minúsculas en registro y login, para evitar cuentas duplicadas.
  • CORS configurado para el frontend en desarrollo (localhost:3000 y 3001).

🕗 Pendiente (mejoras futuras)

  • Rate limiting: limitar los intentos de login por minuto para frenar la fuerza bruta. Aún no está.
  • Token en cookie httpOnly: hoy vive en localStorage/sessionStorage, accesible por JavaScript. Una cookie httpOnly sería más resistente a ataques XSS.
  • Refresh token: renovar la sesión sin volver a pedir la contraseña cuando el token de 30 minutos caduca.
  • CORS de producción y HTTPS: hoy los orígenes son de desarrollo local.
  • Reglas de contraseña y bloqueo de correos desechables en el backend: ahora solo se comprueban en el navegador.
Nota de alcance: este documento describe lo que hay en el código hoy. Las mejoras pendientes se anotan para no afirmar de más; se irán añadiendo en iteraciones futuras.
