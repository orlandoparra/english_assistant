English Assistant

Documento de arquitectura de la plataforma

Última actualización: 7 de noviembre de 2026

1. Visión general

La plataforma usa una arquitectura de dos capas separadas: un frontend (lo que ve el usuario) y un backend (la lógica y los datos). Se comunican por HTTP. 

english_assistant/
├── frontend/   → Interfaz: Next.js + React + TypeScript + Tailwind  (puerto 3000)
├── backend/    → API y datos: FastAPI + SQLAlchemy + SQLite          (puerto 8000)
└── docs/       → Documentación del proyecto (este y futuros HTML)
CapaTecnologíaResponsabilidad
FrontendNext.js 16, React 19, TypeScript, Tailwind 4Páginas, diseño, interacción
BackendFastAPI, SQLAlchemy 2, SQLiteUsuarios, autenticación, datos
SeguridadJWT + Argon2Tokens de sesión y cifrado de contraseñas

Idea clave: layout fijo

layout.tsx es el marco fijo (navbar arriba, footer abajo). Cada page.tsx solo define qué va en el centro. Al navegar entre páginas, solo cambia el centro, no se recarga todo.

    │   ├── user_name_split.py           → split_full_name (nombre/apellido)

    ├── models/
    │   ├── user.py      → Tabla "users" (first_name, last_name, email,
    │   │                   english_level A1–C2, hashed_password, tokens_valid_after)
    │   └── password_reset_token.py → Tabla "password_reset_tokens"
    │                       (hash SHA-256 del token, caducidad, un solo uso)
    ├── schemas/
    │   └── user.py      → Forma de los datos que entran/salen
    └── routers/
        └── auth.py      → Endpoints: /register, /login, /me,
                           /forgot-password, /reset-password, /change-password

Modelo de usuario

Cada usuario guarda first_name y last_name por separado (antes era un único full_name), el email, el english_level (A1–C2, según el Marco Común Europeo) y el hashed_password. Además incluye tokens_valid_after (la Marca de invalidación): todo token emitido antes de ese instante deja de ser válido al cambiar o restablecer la contraseña.

Migraciones sin Alembic

El proyecto usa SQLite sin Alembic. Base.metadata.create_all crea las tablas nuevas, pero no altera las ya existentes. Por eso los cambios de columnas sobre tablas creadas (por ejemplo users.tokens_valid_after) se aplican con scripts de migración idempotentes y transaccionales en app/db/ que solo actúan si falta la columna.

Flujo de una petición en el backend

router (auth.py) → schema (valida datos) → security (cifra/verifica) → model (tabla) → db (guarda o lee)

4. Endpoints disponibles

MétodoRutaQué hace
POST/auth/registerCrea una cuenta. Rechaza correos duplicados.
POST/auth/loginVerifica credenciales y devuelve un token JWT.
GET/auth/meCon el token, devuelve los datos del usuario.
POST/auth/forgot-passwordGenera un token de restablecimiento y envía el enlace (anti-enumeración + rate limit). Responde siempre igual.
POST/auth/reset-passwordRestablece la contraseña con un token de un solo uso e invalida las sesiones anteriores.
POST/auth/change-passwordCambia la contraseña del usuario autenticado tras verificar la actual e invalida las sesiones anteriores.
GET/Comprueba que la API está viva.

5. Cómo se conectan las dos capas

Usuario → Frontend (3000) → petición HTTP → Backend (8000) → Base de datos
                          ← respuesta JSON ←
Ejemplo (login): el usuario llena el formulario → el frontend envía correo y contraseña a /auth/login → el backend verifica y devuelve un token JWT → el frontend guarda el token y lo usa en peticiones protegidas.

6. Conceptos clave

ConceptoQué es
Argon2Algoritmo que cifra la contraseña. Nunca se guarda la real.
JWT"Pase" firmado que identifica al usuario sin reescribir la contraseña. Incluye iat (instante de emisión).
iat + Marca de invalidaciónEl token lleva su hora de emisión; si el usuario cambia o restablece su contraseña, los tokens emitidos antes de ese instante dejan de ser válidos (expulsa sesiones anteriores).
Hash del token de restablecimientoEl token de recuperación se guarda cifrado (SHA-256), nunca en texto plano, para que una filtración de la base de datos no exponga tokens usables.
PydanticValida los datos de entrada automáticamente.
CORSPermiso para que el frontend (3000) hable con la API (8000).
ComponentePieza reutilizable de interfaz (Navbar, Footer, Logo...).
LayoutPlantilla fija que envuelve a todas las páginas.
